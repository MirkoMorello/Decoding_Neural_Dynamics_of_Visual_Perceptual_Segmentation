\section{Software and Hardware Stack}
\label{sec:impl_stack}
Our research was conducted using a modern stack of open-source software and high-performance computing hardware, enabling rapid prototyping and large-scale, reproducible experiments.

\subsection{Core Software Frameworks and Reproducibility}
The entire codebase is built upon Python 3. The primary deep learning framework is \textbf{PyTorch} \cite{paszke2019pytorch}. A core challenge in modern computational science is ensuring that complex software environments are perfectly reproducible, not only over time but also across different hardware and operating systems. A minor difference in a library version can lead to subtle changes in numerical output, threatening the validity of results. This challenge was particularly acute for our project, which required deploying our training pipeline across multiple distinct high-performance computing clusters to accelerate experimentation.

To solve this, we adopted \textbf{Pixi} as our environment and package manager. Unlike traditional approaches that may only specify top-level dependencies, Pixi creates a cryptographically secure "lock file" (`pixi.lock`) that captures the exact version of \textit{every single package} in the environment, including all transitive dependencies, for each target platform (e.g., `linux-64`). This guarantees bit-for-bit reproducibility of the software stack.

Our entire environment is defined declaratively in a `pixi.toml` file. This file specifies:
\begin{itemize}
    \item \textbf{Channels:} The sources for packages (e.g., `conda-forge`, `pytorch`).
    \item \textbf{Dependencies:} A list of all required libraries, such as `pysaliency`, `torch-scatter`, and `segment-anything`.
    \item \textbf{Custom Tasks:} We defined a command alias, `pixi run setup`, which orchestrates a sequence of installation steps. This task first installs the core Conda dependencies, then uses pip to install specific CUDA-enabled PyTorch binaries from their official repository, and finally installs any packages from source, such as the development version of `pysaliency`.
\end{itemize}

This self-contained, declarative approach was fundamental to our workflow. To deploy our code on a new cluster, the only prerequisite was the Pixi executable. Running the single command `pixi run setup` would automatically build the exact same, verified software environment from the lock file, regardless of the underlying system's configuration. This eliminated environment-related bugs, ensured that our results were not artifacts of a specific machine setup, and allowed us to seamlessly scale our research across multiple computational resources, a critical factor in completing the extensive set of experiments required for this thesis.


\subsection{High-Performance Training Techniques}
To maximize the utilization of our hardware and dramatically reduce the wall-clock time required for our experiments, we integrated several state-of-the-art PyTorch features into our core training framework:

\begin{itemize}
    \item \textbf{Distributed Data Parallel (DDP):} Training large Vision Transformer models is computationally intensive. To scale our experiments, we utilized PyTorch's `DistributedDataParallel` (DDP) framework. DDP enables multi-GPU training by creating a separate process for each GPU, where each process holds a complete replica of the model. During training, the dataset is sharded so that each GPU processes a unique portion of the data in each batch. After the backward pass, the gradients from all GPUs are efficiently averaged using the NCCL backend before the optimizer updates the model weights on each process. This ensures that all model replicas remain synchronized. While powerful, DDP introduces specific implementation challenges, such as correct GPU synchronization, avoidance of race conditions, and the need for custom data samplers to ensure correct and efficient data distribution, which will be detailed in \cref{sec:impl_data_pipeline}.

    \item \textbf{Automatic Mixed Precision (AMP):} To further accelerate training and reduce GPU memory consumption, our training loop leverages PyTorch's built-in AMP capabilities via `torch.cuda.amp.autocast` and `GradScaler`. This allows the model to perform many operations, such as the massive matrix multiplications within the transformer, in the faster half-precision (FP16) format. The `GradScaler` component dynamically adjusts the loss scaling to prevent the numerical underflow that can occur with smaller FP16 gradients, thereby achieving significant speedups without sacrificing numerical stability or model performance.

    \item \textbf{PyTorch 2.0 Compile (`torch.compile`):} For an additional performance boost, our models were designed to be compatible with `torch.compile`, a just-in-time (JIT) compiler introduced in PyTorch 2.0. This feature transforms PyTorch code into optimized, low-level kernels by tracing the model's execution graph. It can significantly reduce Python overhead and fuse multiple operations into a single GPU kernel. Achieving compatibility required careful implementation of certain functions, particularly within our custom metrics and data processing, to ensure they were JIT-friendly and could be successfully traced by the compiler. This posed a significant engineering challenge but resulted in substantial runtime improvements, but that couldn't be achieved for all models due to some dynamic control flow that `torch.compile` struggles with.
\end{itemize}
The combination of these techniques was not an afterthought but a core part of our implementation strategy, allowing us to conduct a breadth and depth of experimentation that would have been otherwise intractable.

\subsection{Hardware and Computing Environment}
All model training and evaluation was conducted across a heterogeneous set of high-performance computing resources, a necessity driven by the scale of our experiments and the realities of shared academic infrastructure.

The primary workhorse for our large-scale, multi-day training runs was a SLURM-managed cluster node equipped with \textbf{four NVIDIA A100 (40GB) GPUs}. The large VRAM and high computational throughput of the A100s were essential for training our largest models, particularly DinoGaze-SPADE, using a sufficiently large batch size.

However, access to this primary resource was shared among multiple research groups and was not continuously available. To maintain momentum and accelerate the extensive prototyping, debugging, and ablation studies required by our research, we leveraged two additional, dedicated GPU servers:
\begin{itemize}
    \item A server with \textbf{four NVIDIA TITAN V GPUs}.
    \item A workstation with \textbf{two NVIDIA GeForce RTX 3090 GPUs}.
\end{itemize}

The ability to seamlessly transition our experiments between these three distinct hardware environments was a critical component of our workflow. This was made possible by our rigorous approach to reproducibility. By using Pixi to create identical software environments and by fixing all sources of randomness (including Python, NumPy, and PyTorch random seeds for each DDP process), we could guarantee that a training run initiated on one machine could be reliably continued or replicated on another.

This distributed, multi-cluster approach allowed us to parallelize our research efforts effectively. In total, the computational cost for training, fine-tuning, and evaluating the entire family of models presented in this thesis amounted to several thousand GPU-hours. This significant investment of computational resources underscores the complexity of the models and the thoroughness of the empirical validation performed.




\section[Modular Experimentation Framework]{Modular Codebase Design: A Framework for Rapid Experimentation}
\label{sec:impl_modular_design}

The scientific narrative of this thesis is one of iterative model development, where each new architecture is a direct response to the results of its predecessor. To support this rapid cycle of hypothesis, implementation, and evaluation, we designed our codebase not as a monolithic script, but as a flexible and extensible framework. The core design philosophy was to enforce a strict \textbf{separation of concerns}, ensuring that the logic for defining models, handling data, and executing the training process were fully decoupled. This modularity was the key to efficiently exploring the vast design space of our research questions.

\subsection{The Registry Pattern: A Decoupled and Config-Driven Approach}
At the heart of our design is a simple yet powerful abstraction: the registry pattern. As defined in our `src/registry.py` module, we established two central, global dictionaries: `MODEL\_REGISTRY` and `DATA\_REGISTRY`.

\paragraph{Builder Functions and Registration.} Instead of importing specific model or dataset classes into our main training script, we define a "builder" function for each component in its own self-contained file. This function is responsible for instantiating and returning a fully configured object (e.g., a `torch.nn.Module` or a `torch.utils.data.DataLoader`). Each builder is then registered with a unique string key using a simple decorator, as shown in the example in \cref{lst:registry_example}.

\begin{lstlisting}[language=Python,
caption={Example of the registry pattern for a model builder function. A similar decorator, \texttt{@register\_data}, is used for datasets.},
label={lst:registry_example},
float=tp]
\# In src/models/dinogaze_spade.py
from src.registry import register_model

@register_model("dinogaze_spade")
def build(cfg):
    # ... logic to assemble the DinoGaze-SPADE model ...
    return model
\end{lstlisting}

This pattern is applied identically to our dataset preparation functions. An auto-import mechanism in our main script, `train.py`, ensures that all modules within the `src/models/` and `src/datasets/` directories are loaded at startup, automatically populating the registries with all available components.

\paragraph{Decoupling the Training Entrypoint.} The primary benefit of this pattern is that our main training entrypoint, `train.py`, contains \textbf{no model-specific or dataset-specific logic}. Its sole responsibility is to parse a configuration file, look up the requested model and dataset keys in their respective registries, and pass the configuration object to the corresponding builder functions.

This abstraction turns our framework into a highly flexible experimental platform. To test a new model architecture, one simply needs to create a new file with a registered builder function. To run a new experiment---for instance, training the DinoGaze-SPADE model on the SALICON dataset---one only needs to create a simple YAML configuration file specifying the desired keys. An example configuration file is shown in \cref{lst:yaml_example}. This file defines not only the model and dataset to be used but also all hyperparameters and model-specific options. The training script remains unchanged, as it dynamically constructs the entire experiment based solely on the contents of this configuration file.

\begin{lstlisting}[language=Python,

This config-driven approach allows for the effortless mixing and matching of components, which was instrumental in managing the dozens of experiments, ablation studies, and multi-stage training pipelines required for this research.

\subsection{A Principled Separation of Concerns}
The codebase is structured into distinct, self-contained directories, each with a clear responsibility, reflecting the core components of any deep learning project:

\begin{itemize}
    \item \textbf{Models (`src/models/`):} Each model architecture is defined in its own file. This directory contains not only the final model definitions (e.g., `dinogaze.py`, `deepgaze\_spade\_v3.py`) but also a `common/` subdirectory for reusable components like our custom `SPADELayerNormDynamic` layer.
    \item \textbf{Modules and Layers (`src/modules.py`, `src/layers.py`):} These files contain the fundamental building blocks used to construct the models, such as the `Finalizer` module, the various network heads (saliency, scanpath, fixation selection), and low-level layers like `Bias` and `LayerNorm`.
    \item \textbf{Datasets (`src/datasets/`):} All logic for data loading, preprocessing, and sampling is contained here. Crucially, each dataset builder (e.g., `mit1003.py`, `salicon.py`) is responsible for its entire lifecycle, from downloading raw data to caching and serving batches.
    \item \textbf{Core Training Loop (`src/training.py`):} This is the engine of our framework. It contains a generic, battle-tested training and validation loop that is completely agnostic to the specific model or data being used. It handles checkpointing, logging, metric calculation, and the mechanics of AMP and gradient accumulation.
    \item \textbf{Metrics (`src/metrics.py`):} Standalone, JIT-compatible implementations of all our evaluation metrics (LL, IG, NSS, AUC), ensuring consistent and efficient evaluation across all experiments.
\end{itemize}

This principled structure makes the codebase easy to navigate, maintain, and, most importantly, extend for future research.




\section{Data Preparation and Pipeline}
\label{sec:impl_data_pipeline}
Robust and efficient data handling is critical, especially when working with large datasets, variable image sizes, and iterative training schedules. A naive data pipeline that reads individual files from disk on-the-fly would create a severe I/O bottleneck, leaving expensive GPU resources idle. Our pipeline was therefore designed from the ground up to minimize these bottlenecks and transform raw datasets into a stream of tensors ready for GPU-accelerated training. This process involves several layers of optimization, from initial data serialization to sophisticated batch sampling strategies.
\subsection{Offline Preprocessing: Caching for Performance}
\label{sec:impl_caching}
The raw MIT1003 and SALICON datasets consist of tens of thousands of individual image and data files. To avoid the immense overhead of repeatedly parsing these files, our framework relies on a one-time, offline preprocessing step that converts the datasets into highly optimized, cached formats. This conversion is handled by our dataset builder functions and is DDP-aware: the master process is responsible for creating the cache, while all other processes wait for its completion, ensuring data consistency.
\begin{itemize}
\item \textbf{Image and Center-Bias Caching with LMDB:} To achieve maximum I/O performance for image data, we serialize the entire collection of images and their corresponding pre-computed center-bias maps into a Lightning Memory-Mapped Database (LMDB). LMDB is a high-performance, transactional key-value store that allows for extremely fast, concurrent data reads with minimal memory overhead. By consolidating thousands of small files into a single, large database file, our PyTorch DataLoader can access the data far more efficiently than by interacting with the underlying filesystem, significantly accelerating the start-up and iteration time of our training runs.
\item \textbf{Fixation and Scanpath Data Serialization:} The structured scanpath data, which is smaller and has a more complex relational structure, is separately serialized using pickle. This creates compact cache files (e.g., stimuli.pkl, scanpaths.pkl) that contain the pysaliency objects, which can be loaded into memory quickly at the start of a run.
\end{itemize}
\subsection{PyTorch Dataset Abstractions}
\label{sec:impl_dataset_classes}
At the core of the data pipeline are several torch.utils.data.Dataset classes, designed to abstract away the details of data retrieval and serve the specific needs of our different models.
\begin{itemize}
\item \textbf{Base Classes (ImageDataset and FixationDataset):} These serve as the foundation for spatial and scanpath prediction, respectively. The ImageDataset is responsible for retrieving a sample by index, which consists of an image, its pre-computed center-bias map, and the aggregated fixation map for all observers. The FixationDataset extends this by retrieving individual fixations along with their corresponding scanpath history (e.g., the coordinates of the previous four fixations). Both classes are designed to read directly from the optimized LMDB and pickle caches.
\item \textbf{Segmentation-Aware Subclasses:} To facilitate our experiments with SPADE, we implemented `ImageDatasetWithSegmentation` and `FixationDatasetWithSegmentation`. These classes inherit all the functionality of their parents and add one critical step: they additionally load the corresponding pre-generated unsupervised segmentation mask for the requested image. To make this mask loading efficient, these classes are designed to read from our pre-compiled "mask banks"---large, memory-mapped files that consolidate thousands of individual mask files, using a header/payload system to handle the variable image sizes of the MIT1003 dataset. This ensures that adding segmentation information introduces minimal I/O overhead.
\end{itemize}
\subsection{Batch Sampling Strategies for Training and Evaluation}
\label{sec:impl_sampling}
The strategy for selecting and grouping data into batches is crucial for both training efficiency and correctness, especially in a distributed setting with variable-sized images.
\paragraph{Custom Shape-Aware Sampling for Training.}
A standard PyTorch RandomSampler is suboptimal for our needs, as it would create batches containing images of different sizes. This would require collating batches with significant padding, wasting GPU memory and computation. To solve this, we implemented a custom ImageDatasetSampler. This sampler first groups all indices in the dataset by their corresponding image shape. It then creates batches by sampling exclusively from within these shape-uniform groups. This strategy minimizes padding and maximizes GPU utilization. Furthermore, it is designed to ensure that during each epoch, the model sees batches constructed from every image in the training set exactly once, a common practice in saliency research to ensure stable training.
\paragraph{Distributed Data Parallel (DDP) Sampling.}
For multi-GPU training, simply wrapping the ImageDatasetSampler is insufficient. The standard DistributedSampler is required to ensure each GPU process receives a unique, non-overlapping shard of the data. However, this conflicts with the goal of shape-aware batching.
We address this with a sophisticated two-level sampling strategy. First, the standard DistributedSampler is used to partition the full dataset and assign a unique subset of indices to each GPU rank. Then, our ImageDatasetSampler is instantiated on each GPU process independently, operating only on its assigned subset of data. This ensures both correct data sharding across GPUs and efficient, shape-aware batching within each individual GPU process.


\section{Unsupervised Mask Generation Pipeline}
\label{sec:impl_mask_generation}

The segmentation masks that serve as the conditional input for our SPADE-based models are a critical asset. As this thesis focuses on the \textit{use} of segmentation information rather than its generation, these masks were created in a large-scale, offline preprocessing step. We implemented two distinct, fully automated pipelines to generate these masks, each leveraging a different state-of-the-art unsupervised approach. Both pipelines were designed to be scalable and were executed on our multi-GPU cluster to process the tens of thousands of images across our datasets.

\subsection{DINOv2 + k-means Pipeline}
Our first pipeline generates segmentations that are intrinsically aligned with the feature space of our primary model. The process is conceptually a form of deep feature clustering:

\begin{enumerate}
    \item \textbf{Deep Feature Extraction:} For each input image, we perform a single forward pass through our frozen DINOv2 (ViT-L/14) backbone. We extract the patch tokens from the final transformer block, yielding a feature map of shape $(H_p, W_p, C)$, where $(H_p, W_p)$ are the number of 14x14 patches and $C$ is the feature dimension (1024).
    \item \textbf{Feature Clustering:} The spatial feature map is flattened into a list of $N_p = H_p \times W_p$ patch vectors. We then apply the K-means algorithm to partition these vectors into a predefined number of clusters ($k=16$). Each patch is thus assigned a single integer cluster ID from 0 to $k-1$.
    \item \textbf{Mask Reconstruction:} The resulting 1D array of patch labels is reshaped back into a low-resolution map of $(H_p, W_p)$. This map is then upsampled to the original image's full resolution using nearest-neighbor interpolation to create the final, crisp integer segmentation mask.
\end{enumerate}
The key advantage of this method is its self-consistency: the boundaries of the generated segments are, by definition, determined by the semantic similarities learned by the same DINOv2 model that will later use these masks for guidance.

\subsection{Segment Anything Model (SAM) Pipeline}
Our second pipeline leverages the Segment Anything Model (SAM), a powerful, prompt-less foundation model for segmentation \cite{kirillov2023segment}. The SAM pipeline is more complex due to the exhaustive nature of SAM's output and required the development of a custom post-processing strategy to distill its results into a usable format.

\begin{enumerate}
    \item \textbf{Exhaustive Mask Generation:} We use the `SamAutomaticMaskGenerator` on each image. This component exhaustively blankets the image with a grid of point prompts, generating a list of all potential objects and parts it can identify. This typically results in a list of several hundred candidate binary masks per image, many of which are redundant or overlapping.
    \item \textbf{Filtering and Non-Maximum Suppression (NMS):} Our custom post-processing function first filters out very small, noisy masks based on a minimum pixel area threshold. The remaining candidates, sorted by their predicted quality score, are then subjected to a form of NMS. We iteratively process the list, and for each candidate mask, we discard any subsequent masks in the list that have a high Intersection-over-Union (IoU) with it (threshold set to 0.8). This step is crucial for eliminating highly redundant, near-identical masks (e.g., slightly different versions of the same car).
    \item \textbf{Final Mask Assembly:} From the diverse set of masks that survive the NMS process, we select the top $k$ (e.g., 64) based on their quality score. These selected binary masks are then "painted" onto a blank integer map, each with a unique ID from 1 to $k$, to form the final, non-overlapping segmentation mask. The background is assigned the label 0.
\end{enumerate}
This pipeline capitalizes on the powerful, general-purpose segmentation capabilities of a large foundation model, providing an external and complementary source of structural information to our DINOv2-based system.

\subsection{Mask Banking for Efficient Loading}
Loading tens of thousands of individual image mask files during training would create a prohibitive I/O bottleneck. To solve this, we pre-processed the generated masks into large, memory-mapped "bank" files. This strategy allows for near-instantaneous, random access to any mask without the overhead of individual file operations. Given the variable image sizes in the MIT1003 dataset, we implemented a robust header/payload system:
\begin{itemize}
    \item A single `.bin` \textbf{payload file} contains the raw, concatenated byte data of all masks.
    \item A corresponding `.npy` \textbf{header file} acts as an index, storing a small array where each row contains the shape (height, width) and byte offset for a specific mask within the payload file.
\end{itemize}
During training, the `Dataset` class memory-maps both files. To retrieve a mask, it simply reads the header to find the correct offset and shape, then performs a single, direct memory read from the payload file. This design was essential for achieving the high-throughput data loading required for efficient GPU utilization.




\section{Training and Evaluation Orchestration}
\label{sec:impl_orchestration}

The complexity of our experimental design—involving multiple model architectures, a three-phase training protocol, and a 10-fold cross-validation scheme—made manual execution infeasible and prone to error. To address this, we developed a robust, automated framework to manage the entire experimental lifecycle, ensuring consistency, resilience to hardware failures, and complete reproducibility.

\subsection{The Experiment Orchestrator (`orchestrator.py`)}
The entire research program is driven by a single master script, `orchestrator.py`. This script acts as a high-level conductor, transforming a declarative definition of the entire experimental pipeline into a sequence of executable training jobs.

\paragraph{Declarative Pipeline Definition.} The orchestrator is controlled by a master `pipeline.yaml` file, which defines the complete sequence of training stages. Each entry in this sequence specifies the type of stage (e.g., a single run or a cross-validation loop), the path to its specific configuration file, and its dependencies on previous stages. This declarative approach allows the entire experimental design to be version-controlled and easily modified.

\paragraph{Automated Stage Management.} For each stage defined in the master pipeline, the orchestrator performs several critical tasks:
\begin{enumerate}
    \item \textbf{Configuration Parsing:} It parses the stage-specific configuration file (e.g., `dinogazev1\_sam1\_salicon\_pretrain.yaml` \cref{lst:yaml_example}) which contains all hyperparameters, model keys, and dataset keys for that run.
    \item \textbf{Dynamic Overrides:} For cross-validation loops, it dynamically injects the current fold number into the configuration. This allows a single template config file to be used for all 10 folds.
    \item \textbf{Dependency Management and Checkpoint Chaining:} The orchestrator's most crucial function is automating the "Load-then-Freeze" transfer learning logic. It identifies the best-performing checkpoint from a completed prerequisite stage (e.g., the `final\_best\_val.pth` from the SALICON pre-training) and automatically injects its path as the `resume\_ckpt` argument for the subsequent fine-tuning stage. This ensures a seamless and correct flow of weights between training phases.
    \item \textbf{Execution Invocation:} Finally, it constructs and executes the correct command-line call, invoking the main training script using `torchrun` for DDP or standard `python` for single-GPU runs.
\end{enumerate}
This orchestration system transforms a complex, multi-day workflow into a single, fire-and-forget command, which was essential for managing the hundreds of individual training runs required for this thesis.

\subsection{The Core Training Loop}
The main entry point for any single training job, `train.py`, is a lightweight wrapper that uses the registry pattern to build the specified model and dataset from the configuration. It then delegates control to the generic, battle-tested training loop in `src/training.py`. This core loop manages the entire training lifecycle and incorporates modern best practices for performance, stability, and resilience.

\begin{itemize}
    \item \textbf{Automatic Mixed Precision (AMP):} As stated previously, our training loop leverages PyTorch's built-in AMP capabilities via `torch.cuda.amp.autocast` and `GradScaler` to accelerate training and reduce GPU memory consumption without sacrificing numerical precision.

    \item \textbf{Gradient Accumulation:} To ensure stable training and fair comparisons across different hardware, we needed to maintain a consistent effective batch size. However, the varying memory capacities of our GPU environments (A100s, TITAN Vs, RTX 3090s) or number of GPUs in each cluster meant that batch size is not fixed. We solved this by implementing gradient accumulation. The loop performs several forward and backward passes on smaller "micro-batches" and accumulates their gradients before performing a single optimizer step. For example, to simulate an effective batch size of 32, a system with 4 A100s might run with a per-GPU batch size of 8 and 1 accumulation step, while a system with 2 GPUs and less VRAM might use a batch size of 4 and 4 accumulation steps. This technique is known to be an effective strategy for simulating large batch sizes and stabilizing training for large models \cite{NIPS2012_c399862d}.

    \item \textbf{Resilient Checkpointing:} Long training runs are susceptible to interruptions, such as cluster preemption or hardware failures. Our checkpointing strategy is designed for maximum resilience and automation. The logic, implemented within the `train\_stage` function of `train.py`, follows a clear priority order when a job starts, as illustrated as pseudocode in \cref{lst:checkpoint_logic}.
    
    \begin{lstlisting}[language=python,
    caption={Pseudocode for the checkpoint resumption logic, illustrating the priority system for transfer learning versus recovering from an interruption.},
    label={lst:checkpoint_logic},
    float=tp]
# Checkpoint logic inside train_stage()
def determine_starting_checkpoint(stage_config, stage_output_dir):
    # Priority 1: Check for a local checkpoint in the current stage's output directory
    local_checkpoints = sorted(stage_output_dir.glob('step-*.pth'))
    if local_checkpoints:
        print(f"Resuming interrupted run from: {local_checkpoints[-1]}")
        return local_checkpoints[-1] # Resume the local run

    # Priority 2: If no local checkpoint, check for an external 'resume_ckpt'
    # This is used for transfer learning between stages (e.g., fine-tuning)
    elif stage_config.resume_ckpt:
        print(f"Starting new fine-tuning stage from: {stage_config.resume_ckpt}")
        return stage_config.resume_ckpt # Start a new stage from a previous one
    
    # Priority 3: No checkpoints found, start from scratch
    else:
        print("No checkpoints found. Starting training from random initialization.")
        return None
    \end{lstlisting}
    
    This ensures that an interrupted run will always pick up from where it left off, while a new fine-tuning stage will correctly load the weights from its designated prerequisite, as managed by the orchestrator.

    \item \textbf{Comprehensive Logging:} All relevant metrics (training loss, validation scores, learning rate) are logged to both the console and a `pandas` DataFrame, which is saved as a CSV file after each epoch. This provides a detailed, parsable record of the training history. Additionally, all metrics are logged to a \textbf{TensorBoard} instance for real-time \cite{tensorflow2015-whitepaper}, interactive monitoring of training progress and model behavior.

    \item \textbf{Dual-Condition Early Stopping:} To prevent overfitting and use computational resources efficiently, our training loop employs a dual-condition stopping strategy. Training continues until either of two conditions is met:
    \begin{enumerate}
        \item The learning rate, managed by a `MultiStepLR` scheduler, decays below a predefined minimum threshold (e.g., `1e-7`), indicating that the model has reached a plateau in the optimization landscape.
        \item The primary validation metric (typically Log-Likelihood) fails to improve for a specified number of epochs, defined by the `early\_stopping\_patience` parameter.
    \end{enumerate}
    Upon termination, the script automatically identifies and saves the checkpoint corresponding to the best validation performance achieved during the entire run, ensuring that our final model represents the optimal state of convergence.
\end{itemize}
